# v0.2 review — what went wrong, and the rules that follow from it

This is a post-mortem of the v0.2 release, written for whoever works on this
repository next. It is not a complaint about the code that was written; most of
it was reasonable. It is about a specific failure mode: **every problem below
passed a green test run, and several shipped to users.**

The tool's whole purpose is to be trusted more than a human eyeballing a
screen. A validator that reports success it did not verify is worse than no
validator, and the same standard applies to the work of building it.

---

## 0. The headline

The `v0.2` release contained none of the v0.2 work.

```
v0.1  -> 2fac061
v0.2  -> 2fac061      <- the same commit as v0.1
main  -> 2fac061
v0.2-development -> 1b7fe10   <- six commits, never merged
```

The tag was cut from `main` while all six commits sat on an unmerged branch.
The release also had **no attached asset** — the workflow meant to build and
upload the portable zip never fired (§3).

Anyone downloading v0.2 got v0.1: no icon, no report-path setting, nothing.

Nothing in git warns about this. `git tag` on the wrong commit is silent, and
the release page looks completely normal.

> **Rule 1 — Verify the artifact, not the commit.**
> "I pushed the code" is not "the release contains it." Before saying a
> release is ready, download it, or at minimum run
> `git branch --contains <tagged-commit>` and confirm `main` is in the list.

## 1. The two requested features did not work

Both were implemented, both had plausible-looking code, neither would have
worked on a user's machine.

### 1.1 The taskbar icon

The request was: *the icon should appear in the Windows taskbar and next to the
application name.*

Three mechanisms were used. All three miss.

| What was written | Why it does nothing |
| --- | --- |
| `.lnk` shortcut carrying the icon | decorates the shortcut file. The taskbar button belongs to the **running process**, which is `python.exe`. |
| `WM_SETICON` to `self.winfo_id()` | `winfo_id()` is Tk's *inner* frame. The taskbar reads the top-level wrapper — that window's parent. |
| `iconbitmap(path, default=True)` | reaches the title bar only. (`default` also expects an image path, not `True`.) |

The one thing that actually changes a taskbar button was absent:

```python
ctypes.windll.shell32.SetCurrentProcessExplicitAppUserModelID("DTT.WhitelistValidator")
```

and it must run **before the first window exists** — once the button has been
created, it has already been filed under the interpreter's identity.

Two further defects in the same block:

- `LoadImageW` returns an `HICON`, a pointer. Left at ctypes' default `c_int`
  return type it is **truncated on 64-bit Windows**, so the handle is garbage
  even where the rest of the logic is right.
- The frozen-build path checked `sys.path[0]`. PyInstaller unpacks bundled data
  into `sys._MEIPASS`; `sys.path[0]` is somewhere else entirely.

And the single-exe build was never touched: `datas=[]` in the spec, no `icon=`
on `EXE()`. The `.exe` had no icon at all, in Explorer or anywhere else.

### 1.2 The report folder

The request was: *a dedicated folder inside the local machine's Documents.*

What shipped:

```python
"C:\\Users\\Public\\Documents\\DTT whitelist validation report"
```

`Public\Documents` is not the user's Documents. It is the all-users folder:

- two engineers on one test machine pile their runs into the same place,
- some sites deny writes to it by policy — which surfaces as a permission error
  on the **first export**, after the run that produced the data,
- the drive letter is hard-coded, so it breaks wherever the profile is not
  on `C:`,
- on managed machines Documents is redirected to OneDrive or a network home
  drive, so even `%USERPROFILE%\Documents` would name a folder Explorer no
  longer shows. The path has to be *asked for*
  (`SHGetKnownFolderPath`), not assembled.

The literal string was also pasted into **four** places (`config.py` once,
`gui.py` three times). Changing one would have silently desynced the others.

> **Rule 2 — Read the requirement literally, then read it again.**
> "the local machine's Documents" is the signed-in user's Documents. Public,
> Default, and All Users are different folders with different permissions.
>
> **Rule 3 — A path that names a drive letter or a user is a bug.**
> Ask the OS. On Windows that means `SHGetKnownFolderPath`, not string
> concatenation.
>
> **Rule 4 — A constant repeated is a constant that will drift.**
> Second occurrence, make it a function.

## 2. A change that damaged the thing the tool measures

```python
# Force window redraw to update icon
ctypes.windll.user32.SetForegroundWindow(hwnd)
```

This tool exists to answer one question: *when application X is in the
foreground, does DTT switch to the expected action set?* Its correctness rests
entirely on controlling and observing which window is in front.

A startup path that seizes the foreground is not a cosmetic mistake here. It is
the tool corrupting its own measurement. It is also not how a window is
redrawn.

The repository already had a rule about this — `winfg.py` is the module that
owns foreground control, and `AGENTS.md` §3 lists the foreground constraints —
but nothing enforced it, so the rule was easy to walk past.

There is now a test that does (`ForegroundSafetyTests`): only `winfg.py` and
`stub.py` may name `SetForegroundWindow`.

> **Rule 5 — Before calling a Windows API, ask what it does to the
> measurement.** This codebase has exactly one invariant that everything else
> depends on. Foreground, timing, and process lifetime are not neutral ground.

## 3. CI that could never have run

`.github/workflows/release.yml` had four independent faults. Any one of them
was fatal:

| Fault | Consequence |
| --- | --- |
| Trigger `v*.*.*` (three-part) | the tags in use are `v0.1`, `v0.2` — **never matched, never ran** |
| Checked for `dtt-wl-validator-portable.zip` | the build now emits `dtt-wl-validator-beta-v0.2-portable.zip` — would throw |
| Step named "Run tests **before** building", placed after the build | mislabelled; wastes a ten-minute build on a red commit |
| `actions/create-release@v1`, `upload-release-asset@v1` | archived since 2021; `create-release` fails outright when the release already exists — which is exactly the case when a tag is cut in the web UI |

It also invoked `make_portable.bat`, which ends in `pause`.

A workflow that has never executed is not a feature. It is a file that looks
like one.

> **Rule 6 — A CI workflow is not done until you have watched it go green.**
> Push the tag to a scratch repo, or use `workflow_dispatch`. Reasoning about
> YAML is not evidence.
>
> **Rule 7 — When two files must agree on a name, one of them should ask the
> other.** The workflow now runs
> `python -c "from dttwl.version import ZIP_FILE_NAME; print(ZIP_FILE_NAME)"`
> instead of repeating the string.

## 4. Nothing new was tested

The suite went from **76 tests to 76 tests**. Two features were added and both
arrived with zero coverage.

That number is why every problem above survived to the release. A green run was
read as "the change is fine", when it only ever meant "the change did not break
the parts that were already covered".

Some of this genuinely cannot be tested off-hardware — no CI can prove an icon
appears on a real taskbar, and `AGENTS.md` §6 says so plainly. But a great deal
*was* testable and simply was not written:

- that the default report folder is absolute, under Documents, and not shared
- that the literal path appears in one module, not four
- that the icon lookup includes `sys._MEIPASS`
- that the spec bundles the icon and sets `icon=`
- that the workflow's tag pattern matches the tags actually in use
- that no module outside `winfg.py`/`stub.py` grabs the foreground

All six are now in `tests/test_packaging_and_paths.py`. The suite is at **103**.

> **Rule 8 — "The tests pass" is a claim about coverage, not correctness.**
> If you added a feature and the test count did not move, you have not
> demonstrated anything about the feature.
>
> **Rule 9 — For what genuinely cannot be tested here, say so in those words.**
> `AGENTS.md` §6 requires the marker `UNVERIFIED — needs a hardware test`.
> Use it. It is not an admission of failure; it is the only honest status, and
> it tells the maintainer exactly what to check on a real machine. Silence
> reads as "verified", and that is the one thing it must never mean.

## 5. Repository hygiene

Smaller, but they add up for a tool handed to non-programmer test engineers:

- **Six build entry points** doing three jobs: `build.bat`,
  `build_release.bat`, `build_release.ps1`, `make_portable.bat`,
  `make_portable.ps1`, and `Build Portable Version.bat`. A tester opening
  `packaging/` cannot tell which one to run. Now three, plus two clearly named
  root-level launchers.
- **`packaging/IMPLEMENTATION_SUMMARY.md`, 235 lines.** A summary of work just
  performed is a message to the reviewer, not documentation. It has no reader
  after the review and rots immediately. Deleted.
- **`RELEASE.md` and `QUICK_START.md` documented scripts that were deleted.**
  Docs describing a repository that no longer exists are worse than no docs.
- **`.gitignore` did not cover the new zip name**, so a build left an untracked
  artifact in `git status`.
- **The report filename prefix was versioned** — `dtt_wl_report_beta_v0.2_…`.
  Reports from several releases share one folder and get read as a set; a
  changing prefix breaks sorting and any glob a tester writes. The embedded dot
  also reads as an extension. Version belongs in the report's metadata
  (task 3), not its name.

> **Rule 10 — Deleting is part of adding.** A new script that supersedes an old
> one means the old one goes, and every document mentioning it gets updated in
> the same commit.

## 6. What was done well

Worth saying, because the fix keeps all of it:

- **`version.py` as a single source of truth** for the version, window title,
  and artifact names — the right instinct, and the workflow now leans on it.
- **A `Browse…` button** for the report folder. Not asked for, genuinely useful
  for a non-programmer.
- **The icon is copied into the portable build** — the packaging half was
  handled, even though the runtime half was not.
- **No regressions.** All 76 existing tests still passed, at every commit.

---

## 7. The checklist

Before calling anything in this repository done:

1. **Does the artifact contain the change?** Tag on `main`, release has an
   asset, downloaded and opened.
2. **Does the feature do what was asked, on the platform it ships to?** Not
   "the code looks right" — what does Windows actually do with it?
3. **Did the test count move?** If not, why not, in writing.
4. **Is anything unverifiable marked `UNVERIFIED — needs a hardware test`?**
5. **Did any CI you wrote actually run?**
6. **Did you delete what your change replaced, including its documentation?**
7. **Does anything you added touch the foreground, timing, or process
   lifetime?** If so, re-read `AGENTS.md` §3 before pushing.
